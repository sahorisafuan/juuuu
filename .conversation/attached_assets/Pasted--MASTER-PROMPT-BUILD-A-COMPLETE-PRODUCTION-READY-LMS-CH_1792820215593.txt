## 11. ADMISSION, ENROLLMENT, AND FEE POLICIES

Separate these three financial concepts.

### A. One-time admission fee

The student must satisfy the admission policy before being treated as admitted.

The default policy should charge the admission fee once per student, not once per course, unless the administrator deliberately configures a different policy.

Whether the fee must be paid again after a withdrawal or new admission must be an explicit policy decision.

### B. Course-specific enrollment fee

This fee is optional.

The default course-specific enrollment fee may be zero, unless configured by an administrator or authorized teacher.

Only charge it where the course's current policy requires it.

### C. Monthly tuition

Monthly tuition is charged according to the relevant course or billing plan.

The system must support configurable:

- Tuition amount.
- Billing period.
- Invoice generation date.
- Due date.
- Payment deadline.
- Grace period.
- Late-payment status.
- Access restriction policy for overdue tuition.
- Refund and cancellation rules.
- Manual adjustments with audit logging.

If a student enrolls in more than one course, billing must clearly show which invoices and fees relate to each enrollment.

Avoid charging the admission fee or an enrollment fee twice because of retries, redirects, page refreshes, or duplicate requests.

### Payment state and admission state

Do not treat an application as admitted just because the student reached a payment page.

Implement explicit admission statuses, such as:

- `pending`
- `awaiting_payment`
- `payment_verified`
- `pending_approval`
- `admitted`
- `rejected`
- `cancelled`

Use an appropriate subset of these states and document the allowed transitions.

The administrator should be able to configure whether verified admission payments trigger automatic admission or require manual approval.

An invoice should have its own independent status.

A verified paid invoice must not automatically make every course available. Course eligibility and enrollment rules still apply.

## 12. UDDOKTAPAY PAYMENT INTEGRATION

Check UddoktaPay's current official documentation and the merchant-specific details before implementing API calls.

Use a dedicated provider integration module, for example:

`src/lib/payments/uddoktapay.ts`

Create server-side operations for:

- Initiating a checkout.
- Storing the local payment attempt.
- Validating payment return data.
- Verifying a transaction.
- Processing provider callbacks or webhooks where supported.
- Handling duplicate events.
- Reconciling uncertain transactions.
- Recording the final result.
- Safely linking a verified payment to the correct invoice and admission/enrollment records.

Use configuration variables such as:

- `UDDOKTAPAY_BASE_URL`
- `UDDOKTAPAY_API_KEY`
- `UDDOKTAPAY_ENVIRONMENT`

Add any other secrets only where the provider's actual integration requires them.

Do not assume a particular merchant domain or base URL is valid without verification.

### Required payment flow

1. The authenticated student initiates payment for an eligible invoice.
2. The server reads the trusted invoice amount and policy.
3. The server creates a local payment attempt with a unique reference.
4. The server sends the required request to UddoktaPay.
5. The student is redirected to the provider's returned checkout URL.
6. A return redirect or provider notification is received.
7. The server independently verifies the payment through the provider's documented verification mechanism.
8. The server validates the returned payment status, relevant invoice/transaction identifiers, and expected amount.
9. The application records the verified result in a safe transaction.
10. Only then does the relevant invoice become paid and any configured admission/enrollment action take place.

Never trust the browser to determine payment status.

Never allow a user to submit an arbitrary amount, paid status, invoice owner, or transaction reference to obtain course access.

### Idempotency and failures

The payment handler must safely handle:

- Repeated callbacks.
- Duplicate webhook deliveries.
- Multiple tabs.
- Browser refreshes.
- Pending transactions.
- Failed payments.
- Tampered payment amounts.
- Incorrect invoice references.
- Invalid signatures or callback authentication.
- Provider timeouts.
- Temporary database errors.
- Successful payments whose redirect is interrupted.

Do not mark an invoice paid until verification is complete.

Do not discard potentially successful but unresolved transactions. Provide an administrator reconciliation workflow.

Use sandbox mode and test credentials first. Never simulate a successful live payment.

Automated tests may mock the provider adapter at the boundary; production checkout must use the real provider integration.

### Refunds

Implement a refund record and an administrator-controlled refund workflow.

Call a provider refund API only if supported and enabled for the merchant account. Otherwise, provide a documented manual reconciliation workflow.

Never represent a manual refund as a confirmed gateway refund without evidence.
